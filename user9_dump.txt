2) The "Tommy Planner"
**Tommy Planner: System Analysis**

**Executive Summary**
Tommy is not fundamentally a conventional planner or note collection. It is an attention-management system built around the reality that work unfolds recursively: starting one task exposes another, that task reveals several prerequisites, and the original work may temporarily disappear several levels up the hierarchy.

Its defining capability is preserving continuity through that process. Topics can branch to effectively unlimited depth, while current-topic markers, breadcrumbs, subtree views, history, saved paths, groups, and cycle handoff notes help the user return to the correct point without reconstructing their train of thought.

The central implementation is a custom `<plan-organizer>` web component in [PlanOrganizer.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/PlanOrganizer.js), supported by a Mongo-backed API and specialized services for navigation, cycles, references, reminders, reporting, images, import, and export.

**Core Mental Model**
- A **plan** is a navigable workspace containing root topics, groups, a designated current topic, and optional links to subplans.
- A **topic** combines task, note, and container behavior. It has a title, formatted supporting content, status, reminders, images, group membership, references, and children.
- A **subtopic** is a full topic nested beneath another topic. The data model imposes no fixed nesting limit; practical limits are browser and database capacity.
- A **subplan** turns a large branch into its own independently navigable plan while preserving its relationship to the parent.
- A **current topic** is the explicit answer to “Where should I resume?” It can be set for the whole plan or separately for an active group.
- A **cycle** is an execution routine layered over topics. It determines what receives attention, in what order, and for how long.

**Recursive Planning And Resumption**
Tommy models the way investigative and creative work actually expands. A user can begin with a high-level objective, descend through prerequisites and newly discovered work, finish one branch, and then return to the next unfinished branch at the appropriate level.

- Topics are displayed as collapsible bubbles with inline-editable titles and notes.
- Children can be created indefinitely, reordered, moved inside other topics, moved before or after siblings, or returned to the plan root.
- Desktop uses drag-and-drop; mobile provides explicit move controls, ancestor breadcrumbs, and descendant destinations.
- Completing a parent with unfinished descendants triggers a warning and offers to complete anyway or jump directly to the unfinished work.
- Completion timestamps are retained, enabling historical reporting instead of simply hiding finished items.
- Expansion and collapse state is remembered per plan.
- The last route is restored when the planner reopens.
- Topic history keeps the most recent navigation trail and supports back and forward movement.
- History tracking can be paused, allowing temporary exploration without losing the meaningful working path.
- Named breadcrumb paths can be saved, renamed, sorted, reopened, and deleted. These preserve a multi-plan or multi-reference route as a reusable destination.

Deep nesting is handled intelligently. Tommy shows six hierarchy levels on desktop and three on mobile. When a branch becomes deeper, it offers a “View deeper topics” transition that makes the selected branch a temporary local root. The user gets the focus of a separate workspace without losing the surrounding breadcrumb context.

**Current Topic Designation**
The current-topic system is one of Tommy’s most important features.

A plan can designate one topic as its current point of attention. “Go to current” navigates to it, expands its ancestors, enters a virtual subtree when necessary, scrolls it into view, and highlights it. Groups can maintain their own current-topic pointers, allowing each workstream to remember a separate resume position.

This is materially different from assigning a due date or starring an item. It records the user’s mental cursor: the exact point where work should continue after interruption or after completing a deep branch.

**Plans, Subplans, And Navigation**
- Plans can be created, renamed, deleted, pinned, searched, and displayed as top-level plans or as the complete plan collection.
- Home cards show topic counts, completion counts, and progress.
- Frequently accessed plans are tracked and surfaced alongside pinned plans.
- A topic can be converted into a subplan. Its children become root topics in the new plan, while the original topic remains the doorway.
- Existing plans can also be linked as subplans.
- Plan breadcrumbs preserve the parent-to-child navigation chain.
- Returning through breadcrumbs can restore the relevant topic context rather than merely reopening the plan’s top.

This provides progressive decomposition: small work remains inline; larger branches can graduate into plans without breaking the conceptual chain that created them.

**Groups**
Groups create a second organizational axis independent of hierarchy.

- Plan-scoped groups organize topics within one plan.
- Global groups can collect topics from multiple plans into one cross-plan workstream.
- Groups have names, colors, topic counts, filters, and current-topic designations.
- Filtering by a global group displays grouped sections from every participating plan.
- Deleting a group preserves its topics and only removes their group assignment.
- A topic currently belongs to one group, so groups function as categories or workstreams rather than multi-value tags.

This matters because hierarchy answers “What does this belong under?” while groups answer “What kind of attention or context does this require?”

**Cycles**
Cycles turn Tommy’s stored plans into an active working system. The implementation lives primarily in [CycleManager.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/classes/CycleManager.js).

- Users create reusable cycles from an ordered selection of topics, including topics from different plans.
- Each cycle has a default interval, with optional per-topic duration overrides.
- Topics can have arbitrary priority levels. Higher-priority topics are interleaved more frequently into the execution sequence.
- Each topic can have a customized spoken name.
- The active widget shows the current topic, next topic, remaining time, accumulated topic time, priority, and handoff note.
- Users can start, pause, resume, stop, advance, stay for another interval, jump to another cycle topic, or navigate directly to the underlying plan topic.
- Timer completion produces an alarm and optional browser speech.
- Topics can be active, temporarily inactive, finished within the cycle, or removed.
- Finishing a cycle topic can optionally complete the underlying planner topic.
- Replacement mode lets another topic take over a cycle position while optionally completing the old topic, marking it finished or inactive, and swapping group assignments.
- The same planner topic can participate in multiple cycles, with visible membership badges.

Cycles also preserve **handoff notes**. When moving away from a topic, the user can record what was happening, what remains unresolved, or what should happen next. Those notes are retained historically and presented when the topic comes around again. This directly reduces the cost of context switching.

The active session survives navigation and page reloads through session storage and restores in a paused state. It does not currently provide durable cross-device active-session recovery.

**Cycle Statistics**
Cycle statistics measure execution rather than only completion:

- Total productive time for a cycle.
- Productive time by topic.
- Number of working sessions per topic.
- Current session start time.
- Cumulative paused time.
- Lifetime topic statistics retained in each cycle configuration.

Together with completion reporting, Tommy can distinguish “work completed” from “attention invested,” which is valuable for open-ended work where progress does not always produce an immediately completed task.

**References And Reflections**
Tommy supports several relationship types instead of forcing every connection into folders.

- **Subtopics** express ownership and decomposition.
- **Subplans** express a branch large enough to become its own workspace.
- **References** are lightweight links to plans, topics, or subtopics.
- **Reflections** place a synchronized copy of a topic tree somewhere else.
- **Groups** express cross-hierarchy context.

References are embedded directly inside titles or notes as atomic reference objects. A searchable picker browses the complete plan tree. Clicking a reference navigates to the target, restores its context, expands the necessary path, and highlights it. Copy and paste preserve valid reference objects while sanitizing unrelated pasted markup.

The underlying [ReferenceManager.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/classes/ReferenceManager.js) can validate links, count references, calculate statistics, and locate backlinks, although backlink and reference-statistics views are not yet fully surfaced in the interface.

Reflections are substantially more powerful than references. They copy a selected topic subtree into another location while preserving synchronization. Edits to titles, content, and status propagate in either direction; child ordering and newly created descendants are reconciled; the newest update wins when the two sides differ. Reflections can later be unlinked and retained as independent content. The synchronization algorithm is implemented in [sync_reflection.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/api/Tommy/sync_reflection.js).

**Search, Reminders, And Reports**
Search can inspect titles, note content, or both; include or exclude descendants and subplans; and highlight matches. Matching descendants cause their ancestor paths to appear, so search results retain structural context instead of becoming an isolated flat list.

Reminders support completion dates, times, optional spoken announcements, urgency styling, in-app notifications, and escalating horizons from seven days before through the due moment. They are currently browser-session reminders: there is no service worker, server scheduler, or push-notification delivery when Tommy is closed.

The completed-tasks report defaults to the last 30 days, can be global or plan-specific, groups results by plan, displays completion dates and topic breadcrumbs, links back to the original topic, and supports export. Its implementation is in [CompletedTasksReport.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/utils/CompletedTasksReport.js).

**Pictures**
Topics can receive pictures through file selection or direct clipboard paste.

- Images are resized in the browser to a maximum 1600-pixel dimension.
- Transparent images remain PNG; other images are compressed as JPEG.
- The client attempts to keep each image below roughly 3 MB.
- Topic documents retain image metadata while image data is stored separately.
- Images load lazily only when needed, with at most three simultaneous requests.
- IndexedDB caches up to 250 images or approximately 100 MB for seven days.
- Collapsed topics show image indicators; expanded topics show thumbnails.
- Images can be viewed in a full-screen lightbox and deleted.
- Image upload and deletion participate in undo and redo.

The caching layer is implemented in [PlannerImageCache.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/utils/PlannerImageCache.js).

**Import And Export**
Import accepts pasted text or `.md`, `.markdown`, and `.txt` files. Users choose whether imported content belongs at the plan root or beneath a selected topic.

Markdown headings become nested topics, with heading depth determining hierarchy and intervening paragraphs becoming topic notes. Tab-indented outlines are also recognized, with indentation determining parentage. A preview and topic count are shown before committing the import. See [ImportUI.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/utils/ImportUI.js).

Export can begin from an entire plan or a selected topic. Users can include or exclude subtopics, subplans, and reference labels, and can select individual branches. Output is available as heading-based Markdown or a numbered hierarchical HTML outline, with preview, clipboard, and file-download actions. Linked-plan cycles are guarded against during traversal. See [ExportMarkdownGenerator.js](C:/Users/PJuJu/OneDrive/Documents/Work/Joel_Site/Vercel_Example/RedFish/public/Tommy/Planning/utils/ExportMarkdownGenerator.js).

Current export is designed for readable content transfer, not full backup and restoration. It does not preserve every status, reminder, group, cycle, image, or planner-specific relationship.

**Interface Design**
Tommy uses an information-dense but responsive bubble interface with visual badges for completion, reminders, current status, groups, cycles, subplans, reflections, references, content, and pictures. Editing occurs in place, reducing the separation between capturing a thought and organizing it.

Desktop and mobile receive different hierarchy and movement behavior. The interface includes responsive toolbars, mobile drawers, long-press action hints, system dark-mode support, keyboard search, layered Escape behavior, modal focus handling, and practical touch targets.

Undo and redo cover high-impact structural operations, including deletion, movement, subplan conversion, reminders, topic creation, cycle changes, and images. They are targeted operational history, not a universal revision history for all text editing.

**What Sets Tommy Apart**
Tommy’s distinction is the combination of **recursive decomposition, preserved context, and active execution**.

Traditional task managers generally expect work to fit into a shallow project, section, and task structure. Note systems support arbitrary nesting and linking but rarely provide a strong answer to “What should I work on now, and where was I when I stopped?” Timer applications manage focus intervals but are usually disconnected from the structure and history of the work.

Tommy combines those concerns. The tree captures how the problem unfolded; subtree navigation controls visual complexity; current-topic pointers preserve the return position; references and reflections connect knowledge without flattening it; groups provide alternate work contexts; and cycles decide how attention moves through the system.

That makes it particularly well suited to exploratory projects, research, technical investigations, creative work, executive-function support, and any workflow where the next task is often discovered only after beginning the current one.

**Architecture And Readiness**

- There is no real-time collaboration, assignment system, commenting model, recurring-task engine, or calendar integration.
- Reminder delivery depends on the application being open.
- Import and export are not lossless backup mechanisms.

**Bottom Line**
Tommy already contains the foundations of a distinctive standalone product. Its strongest idea is not infinite nesting by itself; it is making deep nesting usable by preserving the user’s place, intent, and re-entry context. The combination of recursive topics, current-topic pointers, virtual subtrees, saved paths, synchronized reflections, cross-plan groups, handoff-aware cycles, pictures, import/export, reminders, and execution statistics gives it a coherent identity: a planner for work that reveals itself as you do it.

4)  Luxury Discount Aggregation Site

**Executive Summary**
The Luxury Discount Aggregation Site, currently branded **My Wife’s Assistant**, is a decision system for discovering unusually strong luxury-retail values across multiple stores. It replaces retailer-by-retailer clearance browsing with one normalized, continuously refreshed view of the market.

Its objective is more specific than “show sale merchandise.” It helps a shopper use a finite budget to find the greatest number of genuinely compelling opportunities: products with both a low final cost and an unusually large gap between original and sale price.

The system begins at the intersection of the **deepest discounts and lowest final prices**. It then accepts moderately higher prices while preserving exceptional discount quality. Only after those opportunities have been reviewed does it relax the required discount depth. This prevents cheap but ordinary markdowns from crowding out rarer, more economically attractive deals.

**The Optimization Philosophy**
The system treats shopping as a constrained, multi-objective search:

1. **Protect the budget.** Current price determines whether an item belongs in the shopper’s feasible range.
2. **Maximize value distortion.** Within that range, the largest reductions from the reference price appear first.
3. **Prefer more opportunities.** Lower final prices let a fixed budget reach more products.
4. **Preserve deal quality before weakening standards.** The progression allows somewhat higher prices within a powerful discount class before moving down to weaker markdowns.
5. **Spend attention only once.** Seen items disappear unless deliberately restored.
6. **Return only when the market has changed.** Cleared areas reopen when genuinely new merchandise arrives.

This is a lexicographic strategy rather than a simple “sort by price” or “sort by percentage” command. A cheap item with a routine markdown does not automatically outrank a slightly more expensive product selling at a fraction of its former price.

The result is a practical approximation of a value-maximizing search: find as many exceptional candidates as the budget can support without diluting the definition of an exceptional deal too early.

**Two-Dimensional Deal Space**
Every product occupies a cell in a matrix formed by **final price** and **discount depth**.

The price ladder is:

- `$0–25`
- `$25–50`
- `$50–100`
- `$100–200`
- `$200+`
- Arbitrary custom minimum and maximum prices

The discount ladder is:

- At least `95% off`, or an original price at least `20×` the sale price
- `90–95% off`, or `10–20×`
- `80–90% off`, or `5–10×`
- `75–80% off`, or `4–5×`
- `66–75% off`, or `3–4×`
- `50–66% off`, or `2–3×`
- `33–50% off`, or `1.5–2×`
- Under `33% off`

These ranges are mutually exclusive and exhaustive. Boundary values cannot appear in two buckets, and no valid markdown falls into a gap. The definitions and conversion mathematics are centralized in [buckets.ts](C:/Users/PJuJu/OneDrive/Documents/Work/CPP/src/lib/buckets.ts) and [discount.ts](C:/Users/PJuJu/OneDrive/Documents/Work/CPP/src/lib/discount.ts).

**Discount Mathematics**
For current price `P` and original price `O`, the system stores:

```text
discount percentage = 1 - P/O
value multiplier    = O/P
```

A `$100` product originally priced at `$500` is therefore `80% off` and has a `5×` multiplier.

The multiplier is especially useful psychologically. “80% off” can feel abstract, while “the original price was five times today’s price” communicates the magnitude immediately. Both are shown so shoppers can use whichever representation is more intuitive.

For products with price variation across size or color, Tommy stores the minimum and maximum current price. Cards say “up to X% off,” and detail pages explain the full range rather than suggesting every variant receives the best price.

**Assisted Progression**
Assisted Progression converts the two-dimensional matrix into a guided review workflow.

- The shopper chooses a price lane or custom budget ceiling.
- The system begins with the deepest available discount class.
- Items inside the class are presented with the least expensive opportunities prioritized.
- Empty combinations are skipped automatically.
- “I’ve reviewed these” explicitly clears the current stage and moves to the next meaningful one.
- A stage is never considered cleared merely because the shopper scrolled past it or left the page.
- When no unseen products remain, the system recommends the next stage.
- Progress persists across sessions for account holders and locally for guests.
- Reset returns the shopper to the strongest value class.
- Custom mode supports arbitrary price and multiplier or percentage boundaries.

The full progression state includes the chosen price range, current discount bucket, cleared buckets, clearance timestamps, and last update time. This makes deal hunting resumable instead of requiring another exhaustive search every visit.

**Why Seen Tracking Matters**
Most shopping systems repeatedly show the same inventory because repeated exposure can eventually create familiarity and purchase pressure. This site uses repetition as a problem to eliminate.

Opening an item or explicitly marking it reviewed records it as seen. “Hide seen” is enabled by default for signed-in shoppers, with controls to reveal seen items or mark the entire current result set as reviewed.

This changes the emotional meaning of browsing. The shopper is not asking, “Did I overlook something somewhere in these hundreds of cards?” The system provides a reliable answer: everything currently shown is either new or intentionally restored.

Cleared stages remain cleared. If new products later enter one, Tommy displays a restrained notification such as “3 new in 75–80% off.” It reopens the opportunity without erasing the shopper’s progress.

**Psychology And Choice Architecture**
The system addresses several recurring weaknesses in online shopping:

- **Choice overload:** The complete sale universe is broken into finite, meaningful cells.
- **Decision fatigue:** Empty and completed cells disappear from the path.
- **Fear of missing out:** Cross-store aggregation and persisted progress create confidence that the strongest available areas were reviewed.
- **Promotional noise:** Retailer-specific banners and merchandising priorities are replaced by consistent mathematics.
- **Repeated-exposure pressure:** Seen inventory is hidden instead of continuously recycled.
- **Anchoring confusion:** Original price, current price, percentage reduction, and multiplier are shown together.
- **Premature compromise:** The guided order preserves strong discount standards before descending into ordinary markdowns.
- **Unbounded vigilance:** Alerts monitor the market without requiring constant manual checking.
- **Accidental completion:** Progress advances through explicit shopper intent, not passive scrolling.

The interface remains an assistant rather than a purchase-pressure engine. It does not transact, manufacture countdowns, or imply that every markdown should be bought. Its job is to surface candidates efficiently and let the shopper decide whether the product itself is desirable.

A markdown is also treated honestly as a reduction from a retailer’s listed reference price, not proof of objective intrinsic value. Aggregation identifies unusually priced opportunities; the product detail view supplies the evidence needed for the final judgment.

## AI Consulting Capabilities: LLM-Augmented Software Development

### Executive Summary

We leverage a multi-LLM workflow to dramatically increase project productivity, code quality, and requirements fidelity. Our process pairs **worker LLMs** (responsible for planning and implementation) with **reviewer LLMs** (responsible for auditing and scoring), creating a rigorous back-and-forth review cycle that catches issues before they reach production. Combined with structured knowledge management, meeting transcription, and persistent context tracking, this approach ensures that every decision is documented, every change is traceable, and every implementation has been scrutinized by independent AI review before a single line of code is deployed.

---

### 1. The Multi-LLM Review Workflow

#### Context Provisioning

Before any work begins, the worker LLM is provided with comprehensive context:

- Client requirements (transcripts, written specs, meeting notes)
- Existing codebase structure and relevant files
- Schema definitions, API contracts, and business rules
- Historical context from the bug fix tracker and enhancement tracker
- Prior decisions and their rationale

This ensures the LLM isn't working in a vacuum — it has the full picture of what exists, what's changing, and why.

#### Plan Creation & Review Cycle

The workflow follows a structured **plan → review → revise → score** cycle:

1. **Worker LLM drafts a plan** — covering schema changes, API design, frontend components, migration strategy, file organization, and edge cases.

2. **Reviewer LLM audits the plan** — evaluating it against requirements, existing architecture, potential conflicts, backward compatibility, security, and completeness. The reviewer assigns a **score out of 10** and provides specific, actionable feedback.

3. **Worker LLM responds to the review** — for each piece of feedback, it either:
   - **Agrees** and updates the plan accordingly, or
   - **Disagrees** and defends its rationale with specific reasoning

4. **Reviewer LLM evaluates the response** — for each defended point, it either:
   - **Accepts the rationale** and moves on, or
   - **Pushes back further** with additional reasoning as to why the defense is invalid

5. **This cycle repeats** until the reviewer LLM assigns a score of **9/10 or higher**.

6. **Human review** — once the AI review cycle converges, the human reviews the final plan and either approves, requests changes, or provides additional context that restarts the cycle.

Only after both the reviewer LLM (≥9/10) and the human are satisfied does work proceed to implementation.

#### Implementation & Review Cycle

The same back-and-forth process applies to the implementation itself:

1. **Worker LLM implements the plan** — writing code across all layers (schema, API, frontend, migrations, documentation).

2. **Reviewer LLM audits the implementation** — checking for correctness, adherence to the approved plan, code quality, edge case handling, security, and potential regressions. Assigns a score out of 10.

3. **Worker LLM responds** — agreeing and fixing, or defending with rationale.

4. **Cycle repeats** until reviewer score ≥ 9/10 and human approval is obtained.

This dual-review system means every piece of work is scrutinized by an independent AI before it reaches the human reviewer, dramatically reducing the number of issues the human needs to catch and ensuring higher quality output.

---

### 2. The Vibe Code Workflow: Structured Knowledge Management

#### Bug Fix Tracker & Enhancement Tracker

We maintain dedicated folders (`enhancement_tracker/` and bug fix tracking) that serve as a **persistent memory of all changes made to the system**. Each entry documents:

- **What changed** — the specific code modification
- **Why it changed** — the business reason or bug being addressed
- **The specific use case being responded to** — if applicable, the client request or user scenario that triggered the change
- **Date and scope** — when the change was made and what it affects

This serves several critical purposes:

- **Prevents regression** — when the AI is asked to make a change, it can reference the tracker to understand what was previously done and avoid undoing prior work. Without this, an LLM might "fix" a problem by reverting a previous fix, creating an endless loop of re-introducing and re-fixing the same issue.

- **Prevents repeated attempts** — if a problem keeps appearing, the tracker shows every approach already tried. This stops the cycle of trying the same solution over and over and forces new approaches.

- **Provides audit trail** — any stakeholder can trace why the system behaves the way it does, back to the original business decision.

- **Cross-session continuity** — when work spans multiple sessions or even months, the tracker ensures context isn't lost between engagements.

#### Meeting Recording, Transcription & AI Querying

All client meetings are **recorded and transcribed**. The transcripts are stored and made available to the LLM, creating a queryable knowledge base of every client conversation. This enables:

- **Context retrieval on demand** — when a question arises about a past decision or requirement, we can ask the LLM to search the transcripts and provide the answer with the relevant context.

- **Direct quote verification** — the LLM can provide exact quotes from the transcript, which we can then locate in the original recording to verify accuracy. This mitigates against hallucinations — if the LLM says "the client requested X," we can verify by finding the exact quote in the transcript.

- **Requirements traceability** — every feature can be traced back to the specific conversation where it was requested, ensuring nothing is lost in translation between client intent and implementation.

- **Post-meeting clarification** — after a meeting is over, if a question arises about a note or decision, we can query the LLM for additional context without needing to follow up with the client.

---

### 3. Persistent Context & Memory System

Across sessions, the LLM maintains a **persistent memory database** that stores:

- **Project architecture decisions** (e.g., hierarchy model, portal types, schema design)
- **Implementation summaries** (files created/modified, key design decisions, setup commands)
- **Client preferences** (terminology, UI conventions, business rules)
- **Bug fix histories** (root cause, fix applied, files affected)
- **Feature completion status** (what's done, what's pending, what's blocked)

This means when a new session starts, the LLM already knows the system's history, architecture, and prior decisions — it doesn't start from scratch. This is what allows us to maintain continuity on a complex, evolving system across months of development.

- **Migration safety** — all schema changes include preview, dry-run, and confirm modes
- **Backward compatibility** — new fields have defaults, existing API calls continue working
